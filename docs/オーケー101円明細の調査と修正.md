# オーケー101円明細の調査と修正（第4段階）

日付: 2026-11-05 / ブランチ: `codex/receipt-ocr-improvement`
基準: `c8f87fabab1a4aad5b0fee7ea0e023039e56f376`

既存のオーケー立川若葉町店の保存済みOCR fixtureを使用した。
Android実機・新しいレシート画像を使わず、通常抽出から欠落する箇所と原因を再現した。

## 原因

対象行は`F NEIE® -F74-1000m| ¥101`。

| 段階 | 基準版での結果 |
| --- | --- |
| 行分類 | `product`。ヘッダーには分類されない |
| 商品用テキストの切出し | 原文のまま残る |
| 名前の正規化 | `F NEIE® -F74-1000m` |
| 商品名の品質評価 | `productMeaningfulScore=-43` |
| 通常抽出の名前検証 | `isGarbageProductName=true`で拒否 |
| 高速構造判定 | 3種類・6点・717円となり、期待する7点・818円に不足 |
| 通常解析の後段 | 差額101円を復元し、既存辞書で「ピーチティー1000ml」へ補正 |

品質評価の低さは、先頭の短い英字Fを伴う日本語なしの文字列と、`000`の連続等への減点による。
弱いOCR名が、店舗別の確認済み別名と照合される前に価格ごと捨てられていた。
金額101円そのものの読み落としや、店舗名分類の問題ではなかった。

## 修正方針と実装

品質スコア・一般的なゴミ文字判定・商品辞書は変更していない。
通常抽出へ既知の店舗情報を渡し、以下の条件がすべて揃う場合だけ価格明細を保持する。

1. 既存のヘッダー・会計・ポイント・数量記述等の除外条件を通る。
2. 同じ店舗の確認済み辞書に、既存の正規化キーでOCR原文が完全一致する。
3. 対応する辞書商品が一意である。
4. 実際に読めた金額が、その商品の確認済み価格ヒントに一致する。

対象辞書は内蔵の`verified_sample`と、利用者が確認した`learned`。
学習済み商品が同名の内蔵商品を優先置換する既存仕様にも対応する。曖昧一致・同じ価格だけの一致は使わない。

抽出時点では`商品名要確認`、`lowConfidence=true`、`candidateOnly=true`として、原文・単価101円・数量1・合計101円を保持する。
正式な商品名と確認状態の判定は、その後の既存の店舗辞書・会計照合に任せる。抽出だけでは自動確定しない。

通常解析の4つのOCRソースと、OCR実行中の高速構造判定に店舗情報を渡した。
高速判定の合計・点数一致条件は変更していない。

## 改善後

- 商品用OCRから通常抽出だけで101/108/284/325円の4明細、7点が残る。
- 高速構造判定は、実際の4明細合計818円・7点で一致する。
- 全体解析は「ピーチティー1000ml」101円を差額復元なしで取得し、OCR原文も保持する。
- 割引22円、小計796円、税63円、支払859円、商品別按分合計859円を維持する。
- OCR実行の模擬統合テストでは、全体＋分割2回の3認識で構造を確定し、商品専用7パスを追加実行しない。
- 101円の行自体が欠けた場合、価格が102円等へ変わった場合、点数が8点へ変わった場合は高速判定が未完了となる。

既存の「101円が欠けている途中結果の高速判定を無効にする」テスト1件は、修正後の完全な抽出結果を検証する期待値へ更新した。
明細欠落・価格違い・点数違いは新規の負例で別々に確認し、不足したまま高速完了させる変更はない。

## 保護範囲と制約

- schemaVersion 12、IndexedDB/LocalStorageの保存処理・キー・学習辞書形式は維持。app.jsは変更しない。
- 本番データを開かず、Node VMと隔離したブラウザの仮データを使用した。
- main・公開中のGitHub Pages・Service Worker・公開バージョンは変更しない。
- 既存の品質判定や曖昧な名前の自動確定条件は緩めない。辞書にない同様の崩れは引き続き採用しない。
- 原文が読めていない101円の商品を、小計との差額だけから通常抽出へ追加しない。
- Android実機での認識速度・文字認識率・操作性は今回も未検証。模擬workerの認識回数を実機の所要時間とは扱わない。

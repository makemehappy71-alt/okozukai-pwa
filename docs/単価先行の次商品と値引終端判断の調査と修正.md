# 単価先行の次商品と値引終端判断の調査と修正（第34段階）

人工OCR文字列・模擬worker・隔離ブラウザの仮データで検証した。実画像・実店舗書式・Android実機からの再現ではない。テスト用の商品・コード・金額を学習辞書へ追加しない。

## 再現した問題

第33段階の数量検証は「コードと商品計→単価」の順だけを扱っていた。次のように単価が先行すると、元の完全な参照IDと計算根拠がそろっていても数量を検証せず、直前の値引額の終端を保留する。

```text
緑茶 (明細ID 00
0100)
2200083271771 1 ¥1,000
(明細ID 000100) 値引
¥100
緑茶 (明細ID 00
0200)
単価 ¥500
2200083271771 ¥1,000
(明細ID 000200) 値引
¥200
小計 3点 ¥1700
合計 ¥1700
楽天ペイ ¥1700
```

元の印字の単価500円と商品計1000円は隣接し、元から完全な参照ID000200がその直後にある。第33段階と同じ条件で数量2を確認できるが、順序が異なることだけで採用できなかった。単価1000円で数量1の場合も同様だった。

## 修正と安全条件

アプリ側は、既存の隣接2行の検証に逆順の呼び出しを追加した。先頭ゼロ付き数字IDの折り返しの直後にある2行だけを対象にし、次の両配置を同じ `receiptOmittedQuantityDetail` で確認する。

- コードと商品計 → 単価。
- 単価 → コードと商品計。

コードと商品計の行、明示単価の行はそれぞれ厳密な別書式なので、行の役割を数値の一致だけで推測しない。2行の間や前後に空行・注記・別単価・数量・別IDがある場合は読み飛ばさない。商品名と折り返しIDの前にある単価を、後の商品へ割り当てる処理も追加しない。

元から完全な個別値引参照が2行の直後にあり、同じ認識元で元のゼロの桁数まで一致することを引き続き必要とする。完全IDの正規化後の一意性、複数参照・空白違いの保留、裸の値引額の局所的な円単位、金額終端の独立した根拠、会計の検査を維持する。

数量は元の商品計÷明示単価が1〜99の整数で厳密一致する場合だけ検証する。コード10〜14桁、¥付き商品計10〜1000000、明示単価1〜1000000、既存の限定した単価書式・NFKCの条件は変更しない。既定値の数量1、点数や支払総額、学習辞書から不足情報を補わない。数量の印字がある行を上書きしない。

解析用コピーだけを既存の「商品名/ID→コード・数量・商品計」の形へそろえ、単価行を商品として数えないようにする。元のコード価格行の金額表記・円・税区分は残す。原文と呼出元オブジェクトは変更せず、単価先行という元の順序、数量省略、ゼロ・括弧・改行も保持する。デバッグの番号マスクは維持する。

第33段階の数量・単価・商品計の再照合と、第32段階の根拠に基づく終端確認・依存候補の取り消しをそのまま使う。参照ID・数量・点数・小計・税・値引・支払額・認識元間の数量/帰属に矛盾があれば自動確定しない。新しい保存項目・保存処理・schema変更は追加しない。

## 残存条件と保護範囲

- ID直後の2連続行と、その直後の元の完全な個別参照が不足する場合は手動確認を残す。離れた単価、商品IDより前の単価、空行や注記を挟む単価を推定して結び付けない。
- 単価/商品計の意味が不明な書式・価格基準の追加条件、割り切れない数量、上限外の数量、ID重複やゼロの桁数違い、会計・認識元間の矛盾も保留する。
- 数量の既定値・点数・総額・学習辞書を新しい根拠にしていない。英数字IDや、元から数量がある行へ例外を拡張していない。
- 実店舗書式・画像からの認識率、Android実機のカメラ/速度/メモリ/操作性は未検証。性能テストは同等性回帰で、実機速度の測定ではない。
- 隔離ブラウザの初回に従来4ケースで時間切れがあった。同一入力・期待値の再実行は合格したが、初回の待機時間変動の原因は未解明。
- app.js、保存処理・キー、schemaVersion 12、学習辞書、Service Worker、公開バージョンは変更しない。実ユーザーデータは開かない。
- 作業ブランチだけへ反映し、main・公開中のGitHub Pages・無関係なZIP・Git管理対象外のテスト成果物は変更対象外。

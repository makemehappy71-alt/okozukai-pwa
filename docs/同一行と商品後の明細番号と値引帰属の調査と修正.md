# 同一行と商品後の明細番号と値引帰属の調査と修正（第12段階）

日付: 2026-11-07 / ブランチ: `codex/receipt-ocr-improvement`
基準: `35ce7842ce278080da4d31afaf334efd3181610b`

商品名と同じ行、または商品後にある明細番号を調査した。今回も人工OCR文字列・模擬worker・隔離したブラウザの仮データで再現しており、新しい実画像や実店舗の印字形式は検証していない。緑茶・コード・価格の組合せはテスト用で、店舗辞書は追加していない。

## 再現した問題

| 配置・経路 | 基準版の結果 |
| --- | --- |
| `緑茶 明細番号 101` と次行のコード価格 | 番号を商品名へ含め、識別用番号として保持しない |
| `緑茶 ¥1,000 明細番号 101` | 末尾の101を商品価格と誤認する |
| `明細番号 101 緑茶` | 商品名まで番号行と扱い、商品を抽出できない |
| 商品名→コード価格→明細番号→商品値引 | 商品後の番号を保持できず、前処理で値引行が消えると次の商品に付ける |
| 名前と番号だけ、値引50円・支払51円 | 番号101を元価格候補や商品行座標の候補にする |
| 店名→商品名→数量単価合計→番号 | 店名と商品名を結合した余分な候補も生成し、明細の範囲と点数を曖昧にする |

検証中には、統合OCRの重複行除去によって2番目の商品名・コード行が消え、番号だけが残る経路も確認した。新しい後置番号処理でそれを直前の商品の別番号と解釈すると、既存の明細が失われる。独立して読めた番号は保持し、矛盾のある番号情報を値引確定の根拠にしないよう保護した。

## 修正した範囲

### 同じ行の番号

既存の `明細番号`、`明細No.`（ピリオド省略可）、`明細ID` と1〜999999の整数を、商品と同じ行の先頭または末尾から分離する。全角数字・ラベルは正規化する。番号を取り除いた商品名・価格だけを既存の数量・単価・コード解析へ渡す。

対応例は次のとおり。

```text
緑茶 明細番号 101
2200083271771 1 ¥1,000

明細番号 101 緑茶 ¥1,000

緑茶 ¥1,000 明細番号 101

緑茶
2200083271771 1 ¥1,000 明細番号 101
```

番号のない価格を補完せず、名前と番号だけから101円の商品を作らない。元価格復元と座標アンカーも同じ分離処理を使い、番号を価格へ流用しない。実際に印字された101円は引き続き価格として扱う。

### 商品後の番号

商品名から、対応する価格・コード価格・数量単価合計までの開始行と終了行を解析中だけ記録する。その直後の独立した番号行を、隣接する商品が一意の場合に対応付ける。

```text
緑茶
2200083271771 1 ¥1,000
明細番号 101
商品値引 ¥100
```

前処理では、番号付きの認識元について値引行を境界として保持し、削除によって番号を次の商品へ移動させない。番号のない従来の認識元のフィルタは維持する。
数量価格の前にある店舗名を商品名の一部として結合しない条件も追加した。

番号が前後両方の商品に隣接し、どちらに属するか決められない場合は自動確定しない。従来の前置形式は、最初の一意な前置番号から同じ形式が続き、直前の商品に既に番号がある場合に維持する。単に番号の順序や連番から配置を決めることはしない。
商品と番号の間に補足行がある場合、商品名と価格の間に番号がある場合も、都合のよい方向へ補完しない。

### 値引照合と保留

既存のコード（コードなしなら商品名）・数量・元価格・明細番号による一意照合を、新しい配置にも適用する。同じ行の番号を除去した後の実際の商品行と、商品後の番号に対応する明細を使い、明示された商品値引や離れた番号参照を照合する。
重複番号、不正番号、番号の矛盾、方向の曖昧さ、未知の参照先、OCR間の値引対応の矛盾がある場合は自動確認・商品別の自動分割を止める。実際の認識元にある番号の矛盾を、別パスの読めた結果で迂回しない。

商品単位が一意でも、印字点数・小計・値引合計・税額・支払額がそろって一致する必要がある。商品名の利用者確認だけで値引先の不足を解消したとは扱わない。
番号や不正情報のフラグは解析中だけに保持し、保存用の分割計画や取引へ項目を追加しない。

モバイル操作には412pxの3ケースを追加した。

1. 商品名と同じ行の番号101/102を表示し、商品名から番号を分離したまま、値引100円/200円・支払900円/800円で分割する。
2. 商品後の番号101/102について同じ照合・確認・分割を行う。
3. 商品後の番号に対し参照先999がない場合は警告を表示し、名前の確認後も分割計画を作らない。

従来の360px・412pxの操作、前置番号、値下、単一/複数値引、税配分と実canvas画素一致も検証した。保存用計画へ番号を追加せず、隔離ブラウザの仮の既存取引・辞書・IndexedDB/LocalStorageの保持を確認した。OCRは模擬であり、実機性能測定ではない。

## 保護範囲と残存問題

- schemaVersion 12、app.js、保存処理・キー、学習辞書、Service Worker、公開バージョンを変更しない。実データを開かず仮データだけを使う。
- 指定作業ブランチだけへ反映し、mainと公開中のGitHub Pagesは変更しない。無関係なZIPやテスト成果物は対象外。
- 商品間の番号で方向が決まらない場合、番号と商品の間に別情報がある場合は原本確認が必要。行順や残った番号による補完はしない。
- 同じ行でも、商品名の途中にある番号、括弧付き番号、英数字ID、複数ラベルがある形式は確定対象に広げていない。
- 一般的なNo.、取引・会員番号は識別に使わない。商品名が欠ける場合は、番号やコードから名前を作らない。
- 実店舗の印字形式、新しい実画像からの番号認識率、Android実機の速度・カメラ・メモリ・操作性は未検証。

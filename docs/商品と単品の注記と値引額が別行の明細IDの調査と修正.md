# 商品と単品の注記と値引額が別行の明細IDの調査と修正（第25段階）

日付: 2026-11-08 / ブランチ: `codex/receipt-ocr-improvement`
基準: `765eef4450a8c64251be50c82ac4109ae8527fab`

人工OCR文字列・模擬worker・隔離ブラウザの仮データで再検証した。実画像・実店舗書式・Android実機での再現ではない。商品名・コード・金額はテスト用で、学習辞書へ追加しない。

## 再現した問題

基準版は「商品」「単品」と値引ラベル・金額が同じ行にあることを前提にする。同じ認識元に完全な商品IDが一意に存在し、会計も整合する場合でも、注記と値引額が別行になると保留する。

```text
緑茶 (明細ID A101)
2200083271771 1 ¥1,000
…
(明細ID A101
) 単品
値引 ¥100
```

通常の1行IDでも「(明細ID A101) 単品」の直後が「値引 ¥100」の場合、またはID・注記・値引がそれぞれ独立した行の場合に再現した。括弧付きの「(単品)」「(商品)」も同様である。ID末尾文字と閉じ括弧が同じ行になる派生形も追加で再現し、同じ安全条件で処理した。

## 修正と安全条件

`receiptDiscountScopeWord` で、注記行が「商品」「単品」または対応する1組の括弧に入った同じ語と完全一致するか判定する。
`receiptScopeContinuation` は現在行の注記、または直後の注記1行に続く、直後の値引額1行だけを確認する。金額は既存の `receiptDiscountScopeNote` を使い、値引・割引・値引額・割引額・値下額・値下げ額と単一の整数金額が明記され、既存の上限を通る場合だけ採用する。裸の金額や、別行に折り返された値引ラベル・金額は結合しない。

`receiptRecoverWrappedIds` では、完全な閉じ括弧付きIDにもこの限定した継続処理を適用し、折り返しIDにも同じ処理を使う。閉じ括弧・注記・値引額の部分は連続する最大3行に限定する。
ID文字の上限は従来の16文字・最大16個の非空断片を維持する。最長の場合は16個のID断片に、閉じ括弧・注記・値引額の3行が続く計19行までになる。行を際限なく探索したり、上限超過の文字を切り捨てたりしない。

採用には以下をすべて必要とする。

- 同じ認識元に、折り返しのない完全なIDを持つ商品名・数量・価格付き明細が一意に存在する。別OCRパス・結合テキスト・任意のIDラベル・学習辞書を根拠の代わりにしない。
- IDの括弧が対応し、注記にも括弧がある場合はその対応も正しい。復元した参照が正しいID付きの個別値引として解析できる。注記のないID、括弧のないID、商品名が参照の前にある行へ新しい例外を広げない。
- 空白付きIDとの競合や重複がなく、復元後も対象が一意である。両側の折り返しを自己証明させない。候補を適用した後に改めて明細の一意性を検証する。
- 印字点数・小計・税・値引・支払額とOCRパス間の割当整合性を検証する。

空行・タブだけの行・別商品・別ID・注記・税・価格などを読み飛ばさない。「商品対象外」「単品取消」や追加条件、複数金額、値引後価格・値引合計・率だけの行も保留する。ID内部のタブ・空白・欠損文字・記号は補修しない。
元の正規化済みOCR原文・注記・タブ・改行、呼出元オブジェクトを保持し、解析用コピーだけを結合する。保存用計画・取引・学習辞書の項目は追加しない。
案内文を「複数行の明細参照は、同じ認識元の完全な印字と照合しました」に変更し、ID自体が1行のケースでも表示内容が正確になるようにした。原本の値引先の確認案内も維持する。

## 残存条件・保護範囲

- 注記や値引額が連続しない場合、追加条件・未知の注記、値引ラベルと裸の金額自体の折り返しは新しい対象に含めない。複数の別行参照が同じIDを共有する場合も重複候補の保留条件を維持する。
- 同じ認識元の完全なID・一意な対応・会計の整合性が欠ける場合は手動確認を残す。
- 実画像の印字位置・店舗書式・認識率、Android実機の速度・カメラ・メモリ・操作性は未検証。
- app.js、schemaVersion 12、保存処理・キー、学習辞書、Service Worker、公開バージョンは変更しない。実データは開かず、仮データだけを使う。
- 指定作業ブランチだけへ反映する。main・公開中のGitHub Pages・無関係なZIP・Git管理対象外のテスト成果物は変更対象外。

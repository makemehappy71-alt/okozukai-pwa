# 商品コード付き価格明細の調査と修正（第7段階）

日付: 2026-11-06 / ブランチ: `codex/receipt-ocr-improvement`
基準: `d5e8e40ce84d2578d9c00ad66ceb433feb1ee3d5`

Android実機を使わず、明細抽出・商品用テキスト切り出し・会計照合を再調査した。既存の商品コード形式と人工OCR文字列で再現した共通処理の不具合だけを修正した。
商品コードは既存fixtureの値をテスト記号として使っており、仮の98円商品と実店舗の商品・価格の対応を新たに登録したものではない。

## 再現した問題

| 入力・経路 | 基準版の結果 | 原因 |
| --- | --- | --- |
| `緑茶`の次行に`2200083271771 2 ¥98` | 通常抽出0件。全体解析も0件・点数不一致 | 通貨付きコード行は価格に3桁以上を要求し、2桁を扱えない |
| 同じ形で`¥1280` | 直接抽出できるが、全体解析では0件 | 商品用テキストのコード行保護がカンマ付き金額だけに対応。別のヘッダー判定でコード行が落ちる |
| 同じ形で`¥1,280,3` | 1280円・数量2・単価640円として取得し、印字小計1280円と一致すれば明細完了になる | コード行の価格正規表現が行末を確認せず、途中までの一致を採用する |
| `¥1280余計な文字` / `¥1280 ¥2560` | 最初の1280円を取得する | 同じ部分一致の問題 |
| `¥12800000` | 途中の1280000円を取得する | 7桁までのキャプチャを完全な金額として扱い、コード経路で上限も検証していない |

## 修正

- 重複していたコード行判定を`receiptProductCodePrice`にまとめ、商品用テキストの切り出しと明細抽出の両方で使用する。
- 通貨記号付きの2桁価格と、カンマなし価格を通常経路で保持する。通貨記号なしは従来どおり正しい3桁区切りのある価格だけを扱う。
- 行全体を検証し、不正なカンマ・余分な文字・複数金額・桁の途中一致を採用しない。既存の通貨正規化、円・税区分記号を維持する。
- 数量1～99と価格10～1,000,000円の範囲を確認する。通常の商品名付き明細にある10円未満除外と、既存の金額上限に合わせる。
- 割り切れるときだけ単価を導出する。数量2・合計99円なら単価未取得0とし、丸めない。
- GUの保存済み`ZZ00083271771 1 3¥1,990`で使う短い通貨前ノイズ許容を維持する。新しい店舗例外・辞書は追加しない。
- 名前がないコード行は`商品名要確認`・確認必須の候補のまま保持し、コードだけで商品名を推測して確定しない。

## 保護範囲と残存問題

- schemaVersion 12と保存形式を維持。app.js、IndexedDB/LocalStorageの処理・キー、学習辞書、Service Worker、公開バージョンは変更しない。
- 実データを開かず、Node VMと隔離ブラウザ内の仮データだけで検証した。
- 指定作業ブランチだけを変更し、mainと公開中のGitHub Pagesは更新しない。無関係なZIPは対象外。
- コードOCR自体の誤認識や、未知のコードに対応する商品名は解決していない。コードだけの明細は原本確認が必要。
- コード行の不正な金額を抽出根拠には使わない。小計等を根拠とする既存の候補復元一般は変更しないため、候補表示は引き続き原本照合が必要。
- 通貨記号も桁区切りもないコード価格、未対応の前後ノイズ、複数金額がある行は解釈を推測せず採用しない。
- 別行の値引・値下処理にも課題を確認した。`テスト商品\n値引 ¥1,280`の直接抽出では280円を拾う。正しい商品価格を決めるには元価格・値引額・値引後価格の区別と会計整合が必要なため、今回の商品コード修正には含めていない。次の調査対象とする。
- Android実機のカメラ・速度・メモリ・操作性、実画像からの文字認識率は未検証。ブラウザのOCR workerは模擬である。

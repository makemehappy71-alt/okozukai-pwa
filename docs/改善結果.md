## 修正内容

- 商品名: 複数の独立OCR系統が完全一致した場合も合意と認める。同一系統の繰返しだけでは確定しない。先頭の不審な数字をfocused候補から消さず、安全判定へ渡す。
- 確認判定: 「エビピラフ」のような短く自然な名称を一律に低品質としない。記号・不自然な容量表記・不自然な名前のガードは維持する。単品でも複数系統による強い根拠の条件を迂回しない。
- 数量・単価: `s*` を `\s*` に直し、単価ラベル・円記号の前後の空白へ対応する。`21 × 単価 ¥ 99 ¥ 198 外` は2点・単価99円・198円となる。整数の乗算関係、先頭数字、数量2〜99の条件を維持する。
- 税額: `8Y 2点 ¥18` のような見出し欠落の行を、印字された通貨・税率・点数・小計との数値関係で限定的に読む。点数が小計にあれば一致を要求し、税額は小計×税率の切捨て値との一致を要求する。差額だけから税額を作らない。
- 店舗名・例外整理: 早期店名判定の独自ブランド一覧を廃し、既存の既知店舗パーサーを利用する。複数OCRの統合結果である正規名「MEGAドン・キホーテ立川店」も同じパーサーで認識する。既存の店舗別商品辞書は変更しない。
- カテゴリ: GUの「Tシャツ」を「シャツ」より先に判定する。商品別・レシート全体の双方を修正する。
- 操作: OCRライブラリの読込に失敗したscript要素を除去し、次回の再試行で新しい読込が始まるようにする。
- 家計簿の動作テスト: 実行後に選択月が2026年9月、分析期間が「月」へ変わる問題を修正。`finally`で仮state・選択月・分析期間を元に戻し、途中でテストが例外終了しても仮データを残さない。

## モバイルと速度

Windows上のEdge（Chromium）をAndroid User-Agent・タッチ・幅360/412pxで実行。**Android実機の検証ではない。** OCR workerは固定テキストを返す模擬実装。

検証した操作:

- PWA初回インストール後のリロード完了から開始し、致命的エラーがない。
- カメラ入力の`capture="environment"`、画像選択、切抜きプレビュー、結果表示。
- 日付2026-10-10・店舗ヤオコー東大和店・合計108円の表示。
- 未確認の商品名の反映を阻止し、訂正・確認後に入力欄へ反映できる。
- OCR完了後のボタン再操作、worker終了、ページの横はみ出しなし、反映ボタン44px以上、画面画像の目視確認。
- 既存取引・保存内容を維持。JavaScriptのpageerrorは0件。

速度について確認できたこと:

- 同じ全体OCR＋分割2回の模擬入力では、ヤオコー・MEGA・GU・Seria・ファーストキッチンの認識呼出しが **8回→3回**。不要な店名OCR5回を省略できる。
- 西友は従来から3回で、増加なし。未知店舗は8回を維持し、店名の再認識経路を残す。
- ブラウザシナリオは分割3回のため認識4回・worker終了1回。
- 上記は呼出し回数の比較。模擬処理の実行秒数を、実機OCRの高速化率や認識精度の改善率として扱わない。

## 残存問題・次段階

1. Android実機での初回/再回OCR時間、通信不安定時、ピークメモリ、発熱、カメラ画像の向き、ソフトキーボード、戻る操作、PWA単独起動は未検証。adb・実機接続は本作業環境にない。
2. 元のレシート画像セットがないため、画像→文字の実認識精度や商品名正解率は未測定。既存OCRテキストの解析精度とは分ける。
3. バーガーキングの不鮮明商品は追加の辞書/座標根拠がなければ「商品名要確認」を維持する。オーケーの不足明細も高速完了にはしない。
4. 拡大canvasを先に多数生成する処理と、最大18候補の部分集合探索が残る。実機プロファイルと同等性の根拠を得てから改善する。
5. キャッシュキー・リリース番号は基準版のまま。公開する段階では別途バージョン/キャッシュ更新と更新シナリオの検証が必要。
6. 既存家計簿テストには常時trueや存在確認があるため、61件すべてが会計の網羅的検証を意味するものではない。

次の実機確認では、同一画像・同一端末で西友/ヤオコー/MEGAの短い・長いレシートと混在税率レシートを使い、初回1回・準備済み状態で3回ずつ、時間・認識回数・商品/数量/単価/税/店名/カテゴリを記録する。公開中のoriginから独立した検証環境で行う。

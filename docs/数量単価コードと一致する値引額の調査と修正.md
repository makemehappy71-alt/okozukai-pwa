# 数量・単価・コードと一致する値引額の調査と修正（第28段階）

日付: 2026-11-08 / ブランチ: `codex/receipt-ocr-improvement`
基準: `75a027405a36f9864cbde6c00da8a2884661c06c`

人工OCR文字列・模擬worker・隔離ブラウザの仮データによる検証。実画像・実店舗書式・Android実機の再現ではない。テスト用の商品・コード・金額を学習辞書へ追加しない。

## 再現した問題

第27段階では、数字だけの別行値引額が数量・点数・単価・コードと重なる場合を保留した。今回は追加の印字として、値引ラベル自体に円単位がある場合を調査した。

```text
緑茶 (明細ID A101)
2200083271771 10 ¥1,000
緑茶 (明細ID B102)
2200083271771 10 ¥1,000
(明細ID A101
) 値引額（円）
100
(明細ID B102
) 値引額（円）
200
小計 20点 ¥1700
合計 ¥1700
楽天ペイ ¥1700
```

数字100が単価100と一致するが、この参照の「値引額（円）」は金額の役割を明示する。基準版は単位付きラベルを認識せず、完全な商品IDが同じ認識元にあっても保留した。同様に、数量2・点数2・先頭ゼロ付きコードの数値100/200との一致を再現した。

## 修正と安全条件

`receiptDiscountLabelOnly` に、「値引額」「割引額」「値下額」「値下げ額」の直後の `(円)` を追加した。全角括弧は既存のNFKCで正規化し、横方向のスペース・タブ、既存の商品/単品の注記、末尾コロンを許容する。金額行は従来と同じ正規の数字1〜100000だけを認める。符号・先頭ゼロ・桁区切り・OCR文字の補修を追加しない。「値引(円)」「数量(円)」「値引額(個)」「値引額(%)」「値引額(円/個)」「値引額[円]」、不一致括弧・追加条件は対象外。

この正確なラベルから読み取った円単位だけを、一時的な内部情報として値引額の検証へ渡す。数量・点数・数量合計・単価・コード等との数値の一致は、その値引ラベルの円単位を確認したときだけ金額として区別する。共通の「金額単位（円）」見出し、別の値引参照、別OCRパスの単位を借用しない。単位なしの既存保留条件は維持する。

次の条件もすべて必要とする。

- 同じ認識元の元の印字に、商品名と同じ行の完全なIDと、直後のコード・明示数量・通貨表記付き価格がある。コードは文字列として一致し、数量・価格・整数単価も一致する。推定数量1や補修コードを証拠にしない。
- 値引参照のIDが、その元の商品明細1件へ一意に対応する。括弧・文字種・大小文字・記号・空白の競合と復元後の一意性を従来どおり検査する。
- 空行・注記・別ID・別商品・会計行を読み飛ばさず、数字の直後に既知の次明細/参照または会計境界がある。認識領域の切れ目や後続の「個」「%」「対象外」、複数数字候補を切り離して採用しない。
- 小計・点数・税・支払額・値引合計・OCRパス間の帰属が整合する。合計だけで金額の役割や対象商品を推定しない。

対象商品の全額以上の値引と、数字だけのIDに一致する数字は今回も保留する。元のID不足・重複した参照・別パス間の矛盾・会計不一致も保留する。

孤立した「商品コード 100」「数量 100」「単価 ¥100」等が別にあるケースでは、ラベルの役割を区別できても既存の商品・会計検査が通らないものがあった。その7例は保留を維持する回帰にした。孤立した「PLU 100」は既存の他の検査を通過するため、この値引ラベルの円単位を確認できる場合だけ帰属を認める。別フィールドに数字があるだけで会計検査を緩和していない。

解析用コピーだけを既存の値引表記へ変換する。元のOCR原文の単位・数字・改行は保持し、入力オブジェクト、保存用計画、取引、辞書の項目を追加・変更しない。

## 残存条件と保護範囲

- 値引ラベル自体の円単位なしで数値が競合する場合、曖昧な単位、数字IDとの一致、必要な元商品印字がない場合は手動確認を残す。
- 複数の独立した参照が同じIDを共有する場合や、認識元の境界・会計・他パスとの整合性が不足する場合は自動確定しない。
- 実店舗の印字書式・画像からの認識率・Android実機のカメラ/速度/メモリ/操作性は未検証。
- app.js、保存処理・キー、schemaVersion 12、学習辞書、Service Worker、公開バージョンは変更対象外。実ユーザーデータは開かない。
- 作業ブランチだけへ反映する。main、公開中のGitHub Pages、無関係なZIP、Git管理対象外のテスト成果物は変更対象外。

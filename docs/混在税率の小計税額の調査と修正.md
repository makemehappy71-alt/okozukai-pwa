# 混在税率の小計・税額の調査と修正（第6段階）

日付: 2026-11-06 / ブランチ: `codex/receipt-ocr-improvement`
基準: `0ac8930fddf2464f0bc428300aa838bc5c01ff93`

Android実機を使わず、既存の混在税率の解析・商品別按分コードを読解し、人工OCR文字列で残存問題を再現した。新しい店舗辞書や商品名・価格・税額の推測は追加していない。

## 再現した問題

次の読み取り文字列では、税率別の対象額・税額はすべて取得できていた。

```text
8%税抜対象額 ¥100
8%税額 ¥8
10%税抜対象額 ¥200
10%税額 ¥20
```

正しい全体小計は100+200=300円、税額は8+20=28円、合計は328円。しかし基準版は最初の100円を全体小計として保持し、100+28=128円を高信頼の合計に選ぶ。
印字合計・決済金額328円を加えると合計自体は328円になるが、小計100円の誤りは残り、2商品を正しく照合・按分できない。
税率別対象額の後に全体の「小計300円」がある場合も、先に取得した100円が優先される。

追加の負例でも以下を再現した。

- 税率別の金額はカンマ・空白を無条件に除去するため、`1,2`を12円、`100 2`を1002円に変換する。
- 税率ラベルに数字の境界がなく、`18%税額`を8%、`110%税額`を10%として扱う。
- 未読・不正・上限超過の税額を印字0円と区別せず、読めた区分だけから混在税率の合計を作る。
- 全体小計300円・印字合計328円があっても、片方の税額が欠けると、残った20円だけで計算した320円を印字合計より優先する。

## 修正

1. 明示的な8%/10%税抜対象額を、その場で全体小計にしない。両区分の対象額・税額が読めた場合に合算し、全体小計が別途印字されていればそちらを維持する。
2. 単一税率の完全な税抜対象額・税額だけがある場合は、従来どおり解析できるようにする。
3. 税率別金額は正しい3桁区切り、または区切りなしの整数だけを採用する。未取得・不正をnullで保持し、印字0円と区別する。
4. 税率別ラベルの先頭境界を確認し、18等の一部を8/10として使わない。
5. 認識した税率区分のいずれかが不完全な場合、税率別の合算・按分情報を使わない。混在レシートの税率別税額を全体税額へ流用せず、隣接税額の再探索でも再採用しない。
6. 不完全な内訳とは別に、`消費税額`や`消費税額合計`として全体税額が印字されていれば利用する。片方の税額や支払額との差から、不足した税額を新たに作らない。

税率別の行番号と混在の有無は解析関数内の一時情報として扱い、保存や公開APIへ追加しない。税率計算による補完も追加していない。

OCR workerは模擬であり、実画像認識率や実機速度の結果ではない。

## 保護範囲と残存問題

- schemaVersion 12、保存処理・キー、学習辞書、app.js、Service Worker、公開バージョンは変更しない。
- 実データを開かず、Node VMと隔離ブラウザの仮データで検証した。
- 指定作業ブランチだけを変更し、mainと公開中のGitHub Pagesは更新しない。無関係なZIPは対象外。
- 不完全・不正な税率別内訳は、内訳による自動合算・税率別按分に使わない。全体合計・全体税額が別に印字されていなければ、原本照合と手入力が必要。
- 今回検証した8%/10%の明示的なラベル以外、未対応の別行レイアウト、矛盾した複数OCRの最適な選択を一般化して解決したものではない。
- 不鮮明な商品名、数量矛盾、割り切れず単価を特定できない明細等の前段階の制約は継続する。
- Android実機のカメラ・速度・メモリ・実機操作と、画像から文字を認識する精度は未検証。

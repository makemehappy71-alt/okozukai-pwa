# 空白と連続記号を含む明細IDの調査と修正（第15段階）

日付: 2026-11-07 / ブランチ: `codex/receipt-ocr-improvement`
基準: `bc0d34a84e066e1fae2cf9c9eb8c093abf0b3b13`

ID内部の空白・連続記号と値引の帰属を、人工OCR文字列・模擬worker・隔離ブラウザの仮データで調査した。新しい実画像や実店舗の印字形式は検証していない。テストの商品名・コード・価格の対応は仮の例であり、辞書へ追加していない。

## 再現した問題

| 入力・経路 | 基準版の結果 |
| --- | --- |
| `明細ID A1 01 緑茶`、次行にコード価格と商品値引 | IDをA1へ切り詰め、01を商品名側へ渡し、値引帰属を自動確定する |
| `(明細ID A 101)`、`明細ID [A 101]` | ID全体の境界があっても、空白を含むIDを保持できない |
| `(明細ID A--101)`等 | 閉じた境界があっても、連続記号を含むIDを保持できない |
| 空白1個と2個が異なるID | 通常の正規化が複数の空白を1個にし、OCR行の重複排除も空白を除去するため、IDの区別を維持できない |

切り詰めの問題は、正常に読めた別パスと、曖昧なIDを含む実際の認識記録を併用した場合にも再現した。読めたパスだけで曖昧な根拠を迂回しない回帰を追加した。

## 修正した識別条件

### 複雑なIDは閉じた括弧を必須にする

内部の半角スペースや連続する `-`・`_` を使う形式は、「明細ID」と明記され、ID全体の境界が1組の対応する括弧で明示される場合だけ対象にする。ラベルと値の全体、または値部分だけを囲む形式を使う。

```text
緑茶 (明細ID A 101)
2200083271771 1 ¥1,000

明細ID [A  101]
緑茶
2200083271771 1 ¥1,000

緑茶 (明細ID A--101)
2200083271771 1 ¥1,000
```

既存の丸括弧・角括弧・【】の対応検査を維持する。値は先頭・末尾が英数字で、少なくとも数字を含み、空白・記号込みで2〜16文字に限定する。ラベルや括弧に接する前後の余白は構文として扱い、ID内部の空白数は保持する。
数字だけの従来の番号と、記号が連続しない従来の英数字IDの条件は維持する。

`A 101`、`A  101`、`A101`は別IDとし、空白を削除・圧縮して照合しない。`A--101`、`A-101`、`A__101`等も別IDとし、記号を減らしたり置換したりしない。数字部分や先頭ゼロを数値化せず、大文字・小文字、O/0、I/1の区別も維持する。
全角互換表記は従来のNFKCで正規化するが、複数の空白を1個にしない。

### 境界がなければ切り詰めない

`明細ID A1 01 緑茶`は、どこまでがIDでどこからが商品名か分からない。A1だけを採用せず、帰属を保留にする。
同様に、境界のないIDの後に英数字から始まる文字列が続く場合は、IDの続きか商品名かを推定しない。英語の商品名や数字で始まる商品名の場合も、括弧等で境界が読めなければ手動確認になる。
内部空白・連続記号を含むIDを、括弧のない値引参照から補完することもしない。

### 前処理・OCR統合・表示

「明細ID」のある行では横方向の空白を保持し、それ以外の行は従来どおり正規化する。タブ等を半角スペースへ変えて、別の有効IDにすることはしない。
OCRの重複行統合は、ID部分について空白数と大文字・小文字を保ったキーを使う。ID以外の文字列の余白・ケース差による従来の統合は維持し、不正なID行も別の正常なID行へ消し込まない。
確認画面のID欄は空白を保持する表示にし、1個と2個の違いを画面でも確認できるようにした。

### 値引照合と保留

商品側と値引参照側で、括弧から読めたID全体が一致する場合だけ照合する。空白1個と2個の不一致、連続記号の欠落、未知のID、重複、OCR間の矛盾は自動確認・商品別の自動分割を止める。
商品コード（コードなしなら商品名）・数量・元価格・印字点数・小計・税額・支払額の照合も引き続き必要とする。学習辞書や商品名の利用者確認によって、帰属不足を解消したとは扱わない。
IDは解析中だけの情報であり、保存用の分割計画・取引・学習辞書に新項目を追加しない。

新規回帰は、前置・同一行・商品後・値部分の括弧、空白1個と2個、空白なしとの差、連続記号・区切り混在、数字区間のID、O/0、全角互換表記、前処理・OCR統合の保持、前後の明示参照、片方だけの値引、OCR順序反転・配置違い、境界のないIDの切り詰め防止を検証した。
未知の参照、空白・記号の欠落、他パスによる迂回、不正なタブ・記号・括弧・ラベル、重複、会計不足、税配分、元価格への誤流用も検証した。
模擬workerの3ケースで統合文字列にも両IDが残ること、終了1回・保存書込0回を確認した。仮の既存取引・辞書・schemaVersion 12も維持した。

ブラウザには412pxの3ケースを追加した。

1. `A 101` と `A  101` を別IDとして表示し、前後の明示参照から値引100円/200円・支払900円/800円を分割計画に渡す。
2. `A--101` と `A__101` を区別して同じ確認・分割を行う。
3. 実際のIDが `A  101` で、参照が `A 101` の場合は警告し、商品名を確認しても分割計画を作らない。

ID欄の空白保持スタイルとテキスト・解析データの一致を検証した。従来の360px・412px、各番号形式・値引・値下・税配分と実canvas画素一致も合格した。隔離ブラウザの仮の取引・辞書・IndexedDB/LocalStorageを保持し、保存用計画にIDを追加しないことも確認した。OCRは模擬である。

## 保護範囲と残存問題

- schemaVersion 12、app.js、保存処理・キー、学習辞書、Service Worker、公開バージョンを維持する。実データを開かず仮データだけで検証する。
- 指定作業ブランチだけへ反映し、mainと公開中のGitHub Pagesは変更しない。無関係なZIPとテスト成果物はコミットしない。
- 閉じた境界がない複雑なID、IDの続きと商品名が曖昧な配置、タブ・改行・未対応記号、英字だけのID、16文字を超えるIDは手動確認が必要。
- OCRが空白数や記号を誤読した場合も自動修復しない。空白の折返しや印字の欠落からID全体を推定しない。
- 実店舗の印字形式、新しい実画像からのID認識率、Android実機の速度・カメラ・メモリ・操作性は未検証。

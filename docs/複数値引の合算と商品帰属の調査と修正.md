# 複数値引の合算と商品帰属の調査と修正（第9段階）

ブランチ: `codex/receipt-ocr-improvement`
基準: `ef16d0c0c39171a900e8bd9bd6a97dd2674b62ca`

第8段階で残した複数値引の合算・商品への帰属を、人工OCR文字列と既存のOCR実行経路で再検証した。Android実機・実レシート画像による追加測定は行っていない。

## 再現した問題

| 入力・経路 | 基準版の結果 |
| --- | --- |
| 単品1000円、会員値引100円、クーポン割引200円、小計700円 | 値引100円だけを選び、値引前合計を800円とする。1000円の明細が欠落する |
| 緑茶1000円・商品値引100円、歯ブラシ500円・商品値引200円、小計1200円 | 値引合計300円を取得できず、明細が欠落する |
| 別商品に100円ずつの値引、小計1300円 | 同じ金額を1種類とするため、合計200円を取得できない |
| 内訳100円・200円と「値引合計300円」の併記 | 内訳と合計を区別せず、頻度・小さい値を優先して100円を選ぶ |
| 「値引合計」の印字だけが支払合計に似る場合 | 会計解析が値引合計を支払合計の候補にする。小計と同額なら、独立した支払額の証拠としても使われ得る |

修正途中のブラウザ検証では、支払用の連結テキストに同一の1280円値引が2回入るケースも確認した。これは別々のOCR結果を連結したものであり、一つのレシートに2件の値引がある根拠ではない。実際のOCRパスを区別する回帰を追加し、従来の単一値引を維持した。

## 合算の根拠

従来の単一値引関数の戻り値を、無条件の合算へ置き換えてはいない。全体解析に、複数値引・値引合計・不正な値引根拠を照合する別の処理を追加した。

1. 実際の認識パスが`diagnostics`に残っている場合は、全体・分割・商品領域の各認識結果を集計元にする。連結された支払用テキスト・商品用テキストを独立したパスとは扱わない。
2. パス記録がない入力では、提供された各商品・中段・全体・下段テキストを別々に検証する。同一テキストの重複は一度だけ扱う。
3. 一つのパス内の別々の値引行は、同額でも別の発生として保持する。異なるパスの値引額を足し合わせない。
4. 値引合計は内訳への追加値引ではない。内訳と合計が併記されていれば一致を要求する。印字0、率のみ、不正な桁区切り・複数金額等を無視して残りだけを確定しない。
5. 読めた全商品の元価格・数量、印字点数、小計、税、独立して印字された支払合計/決済金額が整合することを要求する。
6. 元価格合計−小計の差は、印字された値引の合計を検証するためだけに使う。差額から値引を新規生成しない。
7. これらの条件に合う一つの認識元が存在するときだけ合計値引を採用する。不完全な複数パスをつなぎ合わせて、印字されていない合計を作らない。

「値引合計」「割引額合計」「合計値引」は、支払額の候補から除外した。
未来のクーポンと値下後価格は、当日の値引合算へ含めない。実際に円額が併記されていれば、率の表記から計算することなく、その円額を使う。

## 商品への帰属

合計値引を取得できることと、その値引を各商品へ割り当てられることを分けた。

- 独立した点数と価格で単品だと確認できた場合は、合計値引の帰属先が一つに定まる。
- 複数商品の場合は、同じ認識元で「商品値引」「単品値引」「商品割引」等の明示的な商品用ラベルが価格行に隣接し、商品名・元価格・数量で一つの明細だけに対応することを要求する。連続する商品値引は、同じ一意の商品へ集計できる。
- 同名・同額・同数量の商品が複数ある場合、価格だけでどの明細かを決めない。
- 一般的な「値引」「会員値引」「クーポン割引」の位置だけで商品を決めない。
- 同じ値引合計が読めても、実際のOCRパス間で商品への割当が食い違えば帰属を確定しない。
- 値引が商品の全額以上になる場合も、今回の商品別分割の対象にはしない。

帰属が確認できた場合、従来の比例按分で値引額を配る代わりに、確認した商品別値引額を使う。値引後の商品価格を既存の税配分へ渡し、税抜・税込・混在税率の会計を保持する。
商品別値引の個数・範囲・全体合計も分割直前に再検証する。

たとえば緑茶1000円への商品値引100円、歯ブラシ500円への商品値引200円では、値引後900円・300円となる。
8%/10%の税抜対象額が900円/300円、印字税額が72円/30円なら、税込972円・330円となる。

## 根拠が不足する場合

合計だけ分かる場合は`total_only`、合算自体を照合できない場合は`unresolved`として、原本確認の警告を表示する。
商品名が学習辞書や再OCRで確認できていても、値引の根拠を迂回して確認済みへ昇格させない。
明細完了扱いと商品別の自動分割を停止し、学習済み商品による自動確認も解除する。
利用者が商品候補を確認して全体の支出額を入力へ反映することはできるが、帰属不明のまま商品別の分割計画は作らない。

新しい状態・割当情報は解析中の一時情報であり、schemaVersion・取引保存形式・学習辞書形式を変更しない。
従来の単一値引・値下処理は維持する。

## 保護範囲と残存問題

- schemaVersion 12、app.js、IndexedDB/LocalStorageの保存処理・キー、学習辞書、Service Worker、公開バージョンを維持する。
- 実データを開かず、仮データだけで検証した。mainと公開中のGitHub Pagesは更新せず、指定作業ブランチだけを変更する。無関係なZIPは対象外。
- 印字点数・小計・支払額、全ての元価格を照合できない複数値引は原本確認が必要。
- 一つの認識元で合計を照合できない部分OCR、未対応のラベル・税区分付き値引行、価格行の間に別の行が入る帰属、コード行や不鮮明な名前による曖昧な対応は自動帰属しない。
- 複数の同名同額商品、商品全額以上の値引、明示されない会員/クーポン値引の帰属は未対応。商品への帰属が不明な場合、推測で按分しない。
- 高速構造判定へ今回の複数値引合算は追加していないため、追加OCRが省略されない場合がある。
- Android実機の速度・カメラ・メモリ・操作性、実画像からの文字認識率は未検証。認識率や実機性能の改善を主張する結果ではない。
